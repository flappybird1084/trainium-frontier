## Framing (why the list is weighted toward step time)

The ~0.02 local gap to the leaderboard leaders (~0.960 local / 0.967 portal) is a **compute gap**, not a
tuning gap. `repeat-regime.md` established the corpus is NOT a wall (~2.8x more tokens still converts at
~the old exchange rate), so a faster step buys more tokens buys lower bpb. Loss-side architecture delivers
0.002-0.008 apiece and stacks sublinearly; step time is the only axis that can close 0.02. Both external
streams independently found the frontier of this exact benchmark (modded-nanogpt lineage) is now
**systems/kernel work** (FlashAttention-3, Triton fusion, fp8, comms overlap) - i.e. where the leaders are.

Reference constants for reading the magnitudes below: **1% step time ~= 0.0003 bpb**; 1800 s same-config
noise band **~0.0004** (paired); portal = local + ~0.0065; only the LNC=1 8-way launch has ever scored.

## 1. Intra-block NKI engine pipelining (step time - the flagship)

**What.** The step is latency/dependency-bound: ~15% MFU, every engine only 30-60% busy because the matmul
(TensorE) keeps stalling on the "glue" - RMSNorm, QK-norm, RoPE, softmax, ReLU2 - running one op at a time on
the Vector/Scalar engines. Fix: **software-pipeline the tiles inside one fused block kernel** so tile i+1's
matmul issues while tile i's softmax is still running. Mechanism in NKI: express tile work with `affine_range`
(no loop-carried deps -> the compiler pipelines aggressively across engines) + manual SBUF allocation to pin
the coexisting tiles, `compiler.no_reorder`. The AWS performance book explicitly **advises against monolithic
megakernels** on Trainium and recommends composable, pipelined kernels - so the target is intra-kernel
pipelining, not "one kernel for the model."

**Precedent.** Anthropic's own NKI FlashAttention went **24 us -> 8.5 us (3x)** exactly this way; its
bottleneck was explicitly "instruction launch overhead on small vector shuffles" - the same failure mode as
our profile.

**New vs. what we closed.** Our null result (PARRES_T: "nesting kernels gives no overlap, the scheduler runs
bodies serially") was **coarse-grained** - it nested whole kernel *bodies*. Tile-level pipelining is a
different construct we have never built. It is NOT falsified by PARRES_T. Also distinct from own-flash-attn
(closed on strided-DMA NaNs, rule #11) - pipelining uses contiguous DMA only.

**Upside / cost / risk.** The only idea here that can dent 0.02: a 20-30% faster step ~= 0.006-0.009 bpb-equiv,
plus the extra tokens. Highest effort. Open risk: whether the Neuron compiler pipelines *our* op mix as well as
it did for attention. **De-risk for free first** on the new **Neuron 2.29 CPU simulator** (prototype one
fused+pipelined attention or MLP kernel, no Trn2 time, no recompile wait) before committing box-hours.

## 2. Optimizer-in-backward overlap (step time - lever F, well-scoped)

**What.** Today backward finishes, then the optimizer runs (~10% of the step). Instead, update each parameter
the moment its gradient is ready, overlapping the cheap AdamW / embedding / scalar updates onto the
Vector/Scalar engines *during* the backward matmuls. **Refinement (from research):** do NOT overlap Muon's
Newton-Schulz/Polar-Express orthogonalization - it is matmul-heavy and would fight the backward for TensorE;
slot only the cheap updates in, and park Muon's matmuls in TensorE idle windows.

**Status.** Open lever F in `plan-097.md`. Comm overlap was already measured at zero (grad_sync 43-55 ms is
per-collective latency, not bandwidth); only the optimizer part remains.

**Upside / cost / risk.** Bounded to the ~10% optimizer cost -> ~0.0015-0.0025 bpb-equiv. Medium confidence,
well-understood mechanism. Cost: days; requires restructuring the manual all-reduce-then-update into per-bucket
"reduce-then-update-as-ready," which fights the ZeRO-1 optimizer sharding (states are split across ranks).

Sources: optimizer-in-backward https://lightning.ai/pages/community/tutorial/faster-pytorch-training-by-reducing-peak-memory/ ·
PyTorch RFC https://github.com/pytorch/pytorch/issues/67570

## 3. Cheap K/V-reuse multi-hop attention (bpb via step - lever D)

**What.** Multi-hop attention is a real quality win (-0.0083 at fixed steps, depth 12) but LOST overall because
it made the step +15% (full gate 0.9926 vs 0.9852): each hop recomputed K/V. Idea: in the extra hop **reuse the
keys/values** and recompute only Q + attention + out-proj, cutting the hop from ~15% toward ~10%. The full fused
op (`tf_nki::hop_fwd/bwd`) already exists and is verified == eager to ~1%; this is a cheaper variant.

**Upside / cost / risk.** Needs the hop below ~8% overhead to flip from loser to winner; if it lands, ~-0.002
to -0.003. Medium-low confidence (it has to clear a specific cost bar). Cost: 1-2 days for the op variant + 2
gates. Note eval-purity: multi-hop is a pure causal function, legal; use EMA_BLEND <= 0.1 with hops (the earlier
"eval collapse" was the tail-EMA blend, now understood - see `ema-cold-start-bug.md`).

## 4. Cached-logit self-distillation on the repeat pass (bpb - cheap lottery ticket)

**What.** We already see the corpus ~1.4x. On the repeat pass, replace the hard one-hot target with a blend of
the hard label and **our own cached top-k predictions from pass 1** (reading a saved log, ~0 extra forward
cost). Concrete recipe from the "Distilled Pretraining" study: small k (even k=1 beats hard-label), ~50% blend,
and **skip the soft target on the lowest-entropy ~15% of tokens** (train those hard-label only) to avoid the
known induction/low-entropy penalty. This is the "only survivor" of the repeat-regime file (`repeat-regime.md`
idea 2). Storage: top-8/token ~= 5-10 GB host RAM, 512 KB/micro-step; reuses the embedding-sidecar plumbing.

**Honest flag.** Both our own record and the external work say the replicated wins here are mostly output
*diversity* / pass@k, NOT single-pass validation loss; and we are **undertrained, not overfit** at 1.4 epochs
(WD/MIR were monotonically worse) - the regime where this kind of regularizer helps least. So: unknown payoff,
genuinely cheap to try, lowest-confidence bpb pick. Largest implementation of the three bpb ideas.

Sources: Distilled Pretraining (k, blend, token routing) https://arxiv.org/html/2509.01649v1 ·
Born-Again saturation https://arxiv.org/pdf/2407.04600 ·
self-distillation = instance label smoothing https://arxiv.org/pdf/2006.05065

## 5. Token-Order-Prediction (TOP) auxiliary head (bpb - fresh, eval-pure)

**What.** Add one extra linear head during training that predicts *how soon* each vocab token reappears (a
ListNet ranking loss over reappearance distance), then **drop it at eval** so the scored forward is unchanged
(eval-path pure, legal). Reported to beat plain next-token AND to beat multi-token-prediction at a fraction of
MTP's cost (2*D*V FLOPs vs MTP's extra transformer blocks), consistently across 340M/1.8B/7B.

**Honest flag.** We tried MTP and it lost badly (**+0.040**), and the research notes small models benefit less
from auxiliary heads - real risk this diverts capacity and hurts here. But it is a genuinely different objective
than anything we have gated, and cheap. Cost: small - one head + ranking loss + one gate.

Sources: TOP https://arxiv.org/html/2508.19228v2 · MTP overview
https://sebastianraschka.com/llm-architecture-gallery/mtp/

## Sequencing

- **1 and 2** are the ones that can close the gap and match what the leaders do. Idea 1 is the big bet but
  starts **free** on the CPU simulator, so it costs nothing to find out if the compiler pipelines our op mix.
- **3, 4, 5** are cheap unattended gates to run on the idle box in parallel with the kernel work. They are
  thousandths, not the 0.02 - queue them, don't bet on them.
- Method rules unchanged: gates only (1800 s), one change per gate, reference every 4-8 runs, judge by eval bpb
  only, never overwrite the vehicle while a run is in progress (NKI tracer reads source from disk).
