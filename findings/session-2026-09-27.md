## 0. THE RETRACTION, and the rule that prevents it recurring

**`C_PRE3` did NOT show that architecture changes are unaffordable.** I ran a learnable width-3 causal depthwise
conv on the residual stream (the cheap Canon placement, outside the fused layer op), measured **2.93 s/step against
v72's 0.424**, saw it stable from step 2 to step 30 with no eager-fallback message, and concluded:

> inserting ANY torch op into the residual stream between the fused layer ops is unshippable

**That conclusion was withdrawn — and then RE-ESTABLISHED by a clean re-run. Read §8 before acting on this
section.** The short version: the run really was confounded, so the claim could not be supported as measured, but a
clean re-run (`C_CAN3`, 0 fallbacks) gives **2.68 s/step**, so the conv itself costs ~2.27 s of the 2.5 s and the
original conclusion holds. What follows is the confound, which is still worth understanding because it is
structural and it recurs.

Re-reading the log after the same failure mode reappeared elsewhere:

```
scatter x4 unavailable ([NkiDispatch] Python lower_func failed ... ) per-table path
NKI AdamW kernel unavailable ([NkiDispatch] Python lower_func failed ... ) using the PyTorch step
```

The embedding scatter **and the entire optimizer** ran off their fused kernels for that whole run — so *as measured*
none of the 7x could be attributed to the conv. (§8: the clean re-run shows the fallbacks were only ~0.25 s of it.
MUDD-style dynamic residual mixing is therefore priced out again, and the conv's quality question remains
**unanswered, not answered negatively** — that is what `C_CANQ`/`C_REFQ` measure at fixed steps.)

Why it was so easy to miss: `_muon_step` and the AdamW path both do `except Exception: self.use_nki = False`, so
**one kernel that will not lower silently disables the fused optimizer for the rest of the run**, printing a single
line among thousands of log lines.

**Fixed structurally.** `submission_raw/train3_canon.py` now routes all seven fallback sites through
`note_fallback()`, which appends to a `_FALLBACKS` list and, under `NEURON_COMPETITION_R1_NKI_STRICT=1`, raises
instead of degrading. The end-of-run summary prints, next to the headline numbers:

```
!!! NKI_FALLBACKS:   2 - THIS RUN DID NOT USE THE FUSED PATH, DO NOT COMPARE ITS STEP TIME
```

**RULE: before believing any step-time regression, grep the log for `unavailable` and `falling back`.** This is the
third time this project has closed an axis on an implementation detail rather than a measurement — cf. the EMA
cold-start bug (which retracted the compiler-flag/hoist/HDC verdicts) and `Q_ROT`'s straggler zero (which removed
one of two equal stragglers and so tested nothing by construction).

## 1. Score CHECKPOINTS offline, not gates against each other

`experimental/score_ckpt.py` loads saved checkpoints through the vehicle's own `load_for_eval` and scores them with
`prepare.evaluate_bpb` on the local GPU, same tokens and same code for every checkpoint. This is **strictly better
than comparing two gates' in-run numbers**, because it removes both the eval-token-subset difference between runs
and all eval-side noise. v72 reproduced to **all six digits** on a re-run, so the harness is deterministic and the
only remaining noise is the training run itself.

It also rescued a result: `C_MTPB`'s in-run eval **crashed** in `prepare.causality_check` (a NkiDispatch lowering
failure at the 4-row eval shape) with the checkpoint already on disk. The checkpoint is written *before* the
in-run self-checks and is fully EMA-blended, so **a crash there costs nothing** — download and score it.

`experimental/offline_logit_eval.py` is the same idea for pure output-space questions, and answered two of them in
ten minutes against 2x30 min of box time.

## 3. Two of the recon's top recommendations are ALREADY SHIPPED

A fresh pass over modded-nanogpt (the useful source is the **Track-3 optimizer benchmark**, 46 entries scored as
steps-to-a-target-loss with n=8-20 seeds, not the wall-clock records table) returned seven candidates. Reading
`_muon_step` rather than trusting my own description of it:

- **NorMuon** (arXiv 2510.05491, published 3375 -> 3300 steps ≈ −0.0007) **is already there**:
  `v_mean = g.square().mean(dim=red_dim)` is the per-row second moment *of the orthogonalised update*,
  `second.lerp_(v_mean, 1 - beta2)` is its EMA at `beta2 = 0.90`, and the `(v_norm / v_norm_new)` factor is exactly
  the Frobenius renormalisation NorMuon prescribes.
- **Cautious Weight Decay** (arXiv 2510.12402, ≈ −0.0002) **is already there**: `mask = (g * w) >= 0` then
  `w.sub_(lr * g + lr * wd * w * mask)`.

**Lesson: describe the optimizer by reading it, not from memory.** Building either would have produced a null
result easily misread as the mechanism failing here.

Still missing and worth trying: **EMA-Nesterov lookahead** (PR #308, n=20 isolated on plain Muon, ≈ −0.0018) —
built this session and gating. Its collapsed recursion,
`m <- (gamma + (1-gamma)*beta_prev) m + (1-gamma) * applied_update`, was verified against an explicit
reference implementation to **7e-08**, and `beta = 0` reduces **exactly** to the base optimizer.

## 4. A vein worth mining: constants inherited and never swept

Five architecture constants have **never been swept as values** in 628 ledger rows. All were inherited from the
pre-512-width "3090 ladder" champion (10 layers x 256 wide, ~3300 steps) and carried through 70+ versions while the
model roughly doubled and the run lengthened 33%:

- `ROPE_FRAC = 0.5` — three rows exist, all at 0.5. Introduced *bundled* with `KEY_OFFSET` (the pair was −0.0032).
- `ROPE_BASE = 200_000`, `LOGIT_SOFTCAP = 11.0`, `SINK_INIT = log 4` — zero rows for any of them as values.
- **`KEY_OFFSET`'s fraction** (`hq = HD // 4`) — every row covers on/off, glue-vs-kernel, or a schedule; none the
  dose. It is a kernel **parameter**, not a constant in the kernel body, so it costs only a recompile.

The first four change only host-side tables or a learned scalar's init, so they need **no recompile at all**.
Also queued: a **joint** LR scale, because every LR was swept one at a time and a coordinated move explores an axis
no single-knob sweep touches.

## 5. Corrections to earlier findings

- `step-split-2026-09-26.md`'s "host work is 18.3 ms in a 466 ms step = a **4% CPU duty cycle**" is **wrong**, and
  with it the arithmetic that killed the hyperthread hypothesis. Measured live: **all 8 ranks at 96-101% CPU**
  (~89% user time, main thread parked in `futex_do_wait`), `thread_siblings_list` = `0,6 1,7 2,8 3,9 4,10 5,11`,
  and `Cpus_allowed_list = 0-11` for every rank (no pinning). The host is **saturated**, not 4% busy. The
  straggler axis still stays closed, but for the `PACK=4` reason and because 8 ranks on 6 physical cores is
  *forced* (and `LNC=2`/`NPROC=4`, which would fix it, is separately dead at 0.654 vs 0.485 s/step).
- Early steps of a run are **host-bound**: dt starts ~0.65 s and settles to ~0.40 s a few hundred steps in, most
  likely cold page cache on the parquet shards. **Never read a step time before ~step 500.**

## 6. Operational traps hit this session

- **`pgrep -cf <pattern>` inside an ssh command matches the ssh command's own command line.** A wait loop on
  `pgrep -cf neuronx-cc` could therefore never succeed. Use a self-escaping pattern: `neuronx-[c]c`.
- **Never `sed -i` a queue file the runner has open.** It swaps the inode; the runner keeps reading the old one, so
  the edit is invisible *and* every later `>>` append is silently orphaned. Append only, or restart the runner on a
  new file.
- **Never launch while an orphaned `neuronx-cc` is alive.** Killing a run mid-compile and launching 90 s later
  produced a run that died with `argument 'h_in' not supplied` — a half-written cache entry.

## 7. Later the same session: the knob sweep, and what it closed

**`ROPE_FRAC` is a measured INTERIOR OPTIMUM at 0.5 — the axis is closed.** All three points scored offline-exact
against v72's 0.968900, each with 0 fallbacks:

| ROPE_FRAC | val_bpb | steps | Δ (step-adjusted) |
|---|---|---|---|
| 0.25 | 0.990234 | 4410 | **+0.0213** |
| **0.50 (ours)** | 0.968900 | ~4390 | 0 |
| 0.75 | 0.970840 | 4330 | **+0.0015** |

The curve is strongly **asymmetric**: down is ~14x worse than up. Fewer rotating frequency pairs means less
relative-position resolution, and the model clearly wants more of it — so 0.5 is not a free choice but a
*compromise* forced by `KEY_OFFSET` needing stationary dims to shift.

**The RoPE/KEY_OFFSET coupling, which nobody had written down.** `inv_freq[64*RF:] = 0`, so the stationary
(non-rotating) head dims are `[64*RF, 64) ∪ [64+64*RF, 128)`. The kernel shifts dims `hq:2hq`. Keeping the shift
inside the stationary block requires **`hq >= 64*RF` and `hq <= 32`**, so at RF=0.5 the only consistent value is
`hq = HD//4 = 32` — exactly what ships. **`KEY_OFFSET_DIV` is therefore not an independent knob**, and RF > 0.5
admits no valid `hq` at all. This is why the pair was introduced together and priced as one change.

**Partial correction to my own argument:** I used that coupling to predict RF=0.75 would fail and dropped two
arms on it. RF=0.75 *is* worse but only by 0.0015, so the coupling is real yet **mild** — do not use it to dismiss
arms outright. The dropped arms (`C_KO2`, `C_KO8`) stay dropped for being low-value, not impossible.

**What the sweep exposed, and it is the more interesting part:** RF=0.5 and `KEY_OFFSET` were measured *as a
package* at v24 (−0.0032 against RF=1.0/no-KO) and never separated in the ~48 versions since. The whole
"stationary dims" design exists to serve `KEY_OFFSET`, so its own contribution at the current config is
load-bearing and unmeasured. Queued as `C_KO0`.

## 8. The retraction was itself over-corrected — re-measure, don't re-reason

`C_CAN3` re-ran the Canon residual conv with `/tmp/nki_*` cleared, **0 fallbacks**, and the conv verified live
(`num_params` +18,432 = 12 x 3 x 512): **2.68 s/step against v72's 0.41**. So of `C_PRE3`'s 2.5 s excess the
fallbacks were only ~0.25 s and **the conv itself is ~2.27 s**. The original conclusion survives; my retraction of
it over-corrected. The retraction was still procedurally right — that measurement was confounded and could not
support the claim — but the lesson is sharper than "check for fallbacks":

**RULE: when you find a measurement was confounded, RE-MEASURE. Do not assume the confound was the whole story.**

~2.27 s / 24 conv applications = **~95 ms each**, which is the ~60-75 ms-per-eager-op figure, so a torch op placed
between the fused layer custom-ops is **not folded into the compiled graph** on this backend.

**Still open, and now being measured the cheap way:** inside `layer_fwd` the same conv would be nearly free (the
kernel already holds the tile in SBUF and already does a cross-tile carry for `KEY_OFFSET`). So the only question
that matters is whether it helps *at all*, and that does not need a time-budgeted gate — `FRAC_BY_STEPS=1` with a
fixed `NUM_STEPS` makes both arms take the identical LR curve and turns the 6.5x step time into wall-clock rather
than invalidity. `C_CANQ` / `C_REFQ` at 600 steps: ~27 min + ~4 min, against a 1-2 day kernel build.

## 9. Five more never-swept knobs, with mechanisms where there is one

- **`NS_STEPS` = 5**, the Polar Express iteration count, zero rows in 635. It selects a *prefix* of
  `POLAR_EXPRESS_COEFFS`, so lowering it is one token and makes the Muon kernel **cheaper**. Direction has a
  mechanism: the ANVIL 6-map cascade, envelope [0.9951, 1.00041] against our ~[0.86, 1.14], **lost** by +0.00062 —
  so tighter orthogonalisation does not help here, and looser may. **`POLAR_EXPRESS_COEFFS` has only 5 entries**,
  so `ns_steps=6` is bit-identical to the baseline: kept deliberately as a **REPLICATE that measures run-to-run
  training noise**, which every offline delta needs as a floor.
- **The value-embedding DEPTH SCHEDULE.** Three tables assigned as layers `[0,t1)/[t1,t2)/[t2,L)` with
  `t1 = L//3`, i.e. an even 4/4/4 over 12 layers, never swept. The lineage this stack came from concentrates value
  embeddings at the **first and last** layers instead. `VE_T1`/`VE_T2` knobs added; 2/8/2 and 5/2/5 queued.
- **A JOINT learning-rate scale.** Every LR was swept one at a time and each sits on a plateau; the joint
  direction is a different axis, and all four constants were tuned when the run was 25% shorter.
- `ROPE_BASE = 200_000` (vs the conventional 10_000 at this context length), `LOGIT_SOFTCAP = 11.0`,
  `SINK_INIT = log 4` — all inherited from the pre-512-width champion, all zero rows as values.

## 10. Operational

- **`pkill` and `setsid nohup` in the same ssh call kills the thing you just started.** Twice. Start background
  runners in their own call.
- The in-run `causality_check` can **HANG for 30+ minutes** after torchrun has already printed its traceback
  (processes left in `hrtimer_nanosleep`/`futex_do_wait`, no compiler running). `EVAL_PUBLIC=0` avoids it.
- Scoring workflow that works: arm finishes with `EVAL_PUBLIC=0` → check its `NKI_FALLBACKS:` line → rsync the
  822 MB checkpoint (~1 min) → `experimental/score_ckpt.py v72_final.pt arm.pt` → delete the checkpoint.

## 11. The branch campaign: three coordinated jumps, and what they returned

The user asked for "a backtrack and redescent down different optima" — multi-change branches rather than
single-knob perturbations, screened cheaply between the full gates. Three Opus agents each produced one branch,
entirely behind one env flag, with flag-off verified identical to baseline. **The screen protocol**: 600 fixed
steps with `FRAC_BY_STEPS=1` so both arms take the identical LR curve over identical steps, scored against a
measured baseline of **1.1214480**. A slower branch then costs wall-clock rather than validity.

**What each returned:**

| branch | screen (600 steps) | full gate | verdict |
|---|---|---|---|
| **B1** capacity reallocation (hashed-table rank) | **−0.00206** and 67M params deleted | queued | LIVE |
| **B2** optimization regime (wd tracks lrm + 5 coupled changes) | not screened (author said it would mislead) | **−0.00053** step-adjusted | LIVE, confirming |
| **B3** two-tower output mixture | queued for its diagnostic | — | prior is that it loses |
| the canon conv (pre-existing item, in-kernel) | **−0.01366** | **+0.0081** | see §12 |

**B1 is the most interesting result of the session.** Its thesis: *rank should follow visits-per-row*. The
2^18 x 512 hashed bigram table gives 262,144 rows 512 free parameters each, but a typical row is visited a few
hundred times per screen, while the 8192-row token tables get ~10k visits each — those can support 512
parameters, the hashed rows cannot. The author's own **falsifier** (a pure row-width halving at the baseline's
rows and addressing, meant to kill the axis if it lost by >0.001) instead **won by −0.00206 while deleting 67.1M
parameters**, taking the model from 205.5M to 138.5M. It also retro-explains a standing oddity in the ledger:
2^17 -> 2^18 rows won (−0.0023) but 2^18 -> 2^19 lost (+0.0009), which is the signature of rows too **wide** to
train, not of running out of addressing space. And because 46% of the ZeRO-sharded elements disappear, it should
pay a second time in step time (AdamW math, the parameter all_gather, and the embedding sidecar all shrink).

**B2 won but its stated mechanism is refuted.** It argued lr and wd are one knob, because Muon's fixed-Frobenius
update makes ||W|| equilibrate at sqrt(lr/wd), and validated that by predicting our weight-decay rows out of
sample from our LR rows (wd 0.20 predicted +0.0042 vs measured +0.0032/+0.0045). Its falsifier was a norm
diagnostic. Measured: the baseline's Muon norms **grow** for most of the run and then fall only ~10%, with two of
three stacks flat, against a predicted 1.67x decline. So the baseline was never in the sqrt-compressed regime the
argument assumes. B2's own norms are flat to −5% at ~2x the baseline's magnitude, so the intervention did what it
was designed to do — the theory of why that should help is just wrong. **Do not reuse its coupling arguments**,
especially the terminal-LR raise justified as compensating for a norm collapse that does not occur.

**Method note that paid off repeatedly: make the agent ship a falsifier.** All three branches did, and in two
cases the falsifier was more informative than the branch. B1's was a single decisive knob that would have closed
the whole axis in one run (it opened it instead). B2's tested the *reasoning* rather than the score, and caught
that a winning change wins for the wrong reason. B3's measures the mixing gain and the depth penalty separately,
so it stays useful even when the package loses.

## 12. THE METHOD ERROR THAT COST THE DAY: a deterministic screen that is ANTI-PREDICTIVE

I built a fast screen — 600 fixed steps with `FRAC_BY_STEPS=1` so both arms take an identical LR curve — validated
that it was **reproducible**, and used it to rank four mechanisms. It is reproducible: `C_REFQ2` returned
**1.1214479992153266**, bit-identical to `C_REFQ` across all 16 digits, and a repeat of the conv arm returned
**1.1077838573592296**, also bit-identical. Training on this box at fixed steps is fully deterministic, so the
screen's noise floor is **exactly zero** and every delta it reports is exact signal.

**And it still misled me on every architecture question, because determinism is not validity.** The screen measures
a real quantity; it is just not the quantity I care about:

| mechanism | 600 fixed steps | full 1800 s gate | swing |
|---|---|---|---|
| Canon residual conv | **−0.013664** | **+0.0081** | +0.022 |
| B1 hashed-table rank cut (512 → 256) | **−0.002055** | **+0.0039** | +0.006 |
| multi-token prediction | (not screened) | +0.0051 | — |

Two independent mechanisms reversed sign, and the third failed for the same underlying reason. **At 600 steps the
model sits at 1.12 bpb against 0.968 when trained** — it is a different object. Anything that helps an
undertrained model (local token mixing; deleting over-parameterisation it cannot yet use) is a liability to a
better-trained one, where attention has learned the local structure itself and the extra capacity has become
usable. That is exactly the mechanism already in the ledger for why MTP failed: the 134M bigram table covers the
n-gram job *by convergence*, not at step 600.

**RULE: no more short screens for capacity or architecture questions on this project. Full 1800 s gates only.**
A gate is 32 minutes; a screen is ~20 with a cold compile, so the screen was never even much cheaper. Screens
remain valid for two narrow purposes: (a) throughput/step-time measurements, which are horizon-independent, and
(b) checking that two implementations of the *same* mechanism agree, which is a relative question.

**The generalisable mistake**: I verified the screen's *precision* and never its *predictive validity*. Those are
different properties, and a deterministic instrument that measures the wrong thing is more dangerous than a noisy
one, because its consistency reads as trustworthiness. Four mechanisms were ranked, a 1-2 day kernel build was
justified, and a branch was declared "the session's best lead" on the strength of it.

## 13. Where the conv investigation actually ended

The engineering succeeded completely: in-kernel, **zero added kernel launches** (per-tap doc masks ride as extra
columns of the existing `dstart`, conv weights as extra columns of `scal`, weight gradient returns via `dscal`
row 0 into an existing all_reduce), **+4.7% step time** as estimated, bit-exact on device across a 1/2/4/6/7/128
tile sweep, compiles at every shape after one `accumulate=False` fix.

One real gradient bug was found and fixed along the way: the backward returned `Aᵀg` in place of `dL/dxm`, so the
`x0` embedding-skip gradient — which must not pass through the conv transpose — was being pushed through it in
all 12 blocks. The fix is verified by a **model-level** test with a negative control that re-creates the broken
wiring and requires the test to reject it (it does: `dx02` off by 2.0, `d_x0` off by 1.1e3).

**But the fix changed the outcome by 1.3e-06** (600 steps: 1.1200124 fixed vs 1.1200111 broken), and the two
implementations still disagree ~10x at the same horizon (torch −0.01366, kernel −0.00144) with **no identified
cause** after kernel-level *and* model-level equivalence testing. The learned taps rule out the simple
explanations — both implementations learn convs of comparable magnitude (drift from identity 21.1 torch vs 22.5
kernel), so the mechanism is active in both; they converge to different solutions.

**Closing it anyway**, because §12 removes the reason to care: the −0.01366 target was a 600-step number, and
600-step numbers do not predict full length here. The kernel's full-length result is +0.0081 twice. The unexplained
10x remains on the record as an open anomaly rather than a solved one.
