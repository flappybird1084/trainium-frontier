# 2026-09-27: a retraction, two exact closures, and the method that made them cheap

State at the end of this session: **v72 = 0.968134 is still the best**, target 0.9650, gap **−0.0031**. Nothing
shipped. What follows is what is now known that was not known yesterday.

## 0. THE RETRACTION, and the rule that prevents it recurring

**`C_PRE3` did NOT show that architecture changes are unaffordable.** I ran a learnable width-3 causal depthwise
conv on the residual stream (the cheap Canon placement, outside the fused layer op), measured **2.93 s/step against
v72's 0.424**, saw it stable from step 2 to step 30 with no eager-fallback message, and concluded:

> inserting ANY torch op into the residual stream between the fused layer ops is unshippable

**That conclusion is withdrawn.** Re-reading the log after the same failure mode reappeared elsewhere:

```
scatter x4 unavailable ([NkiDispatch] Python lower_func failed ... ) per-table path
NKI AdamW kernel unavailable ([NkiDispatch] Python lower_func failed ... ) using the PyTorch step
```

The embedding scatter **and the entire optimizer** ran off their fused kernels for that whole run. That alone
accounts for the 7x. **None of it can be attributed to the conv.** Also withdrawn, therefore: the pricing-out of
MUDD-style dynamic residual mixing, which is the largest published matched-step delta found in the recon
(−0.0084 nats at fixed steps, n=10 vs n=10). The Canon conv's real cost is **unknown** and its quality question is
**unanswered, not answered negatively**.

Why it was so easy to miss: `_muon_step` and the AdamW path both do `except Exception: self.use_nki = False`, so
**one kernel that will not lower silently disables the fused optimizer for the rest of the run**, printing a single
line among thousands of log lines.

**Fixed structurally.** `submission_raw/train3_canon.py` now routes all seven fallback sites through
`note_fallback()`, which appends to a `_FALLBACKS` list and, under `NEURON_COMPETITION_R1_NKI_STRICT=1`, raises
instead of degrading. The end-of-run summary prints, next to the headline numbers:

```
!!! NKI_FALLBACKS:   2 - THIS RUN DID NOT USE THE FUSED PATH, DO NOT COMPARE ITS STEP TIME
```

**RULE: before believing any step-time regression, grep the log for `unavailable` and `falling back`.** This is the
third time this project has closed an axis on an implementation detail rather than a measurement — cf. the EMA
cold-start bug (which retracted the compiler-flag/hoist/HDC verdicts) and `Q_ROT`'s straggler zero (which removed
one of two equal stragglers and so tested nothing by construction).

## 1. Score CHECKPOINTS offline, not gates against each other

`experimental/score_ckpt.py` loads saved checkpoints through the vehicle's own `load_for_eval` and scores them with
`prepare.evaluate_bpb` on the local GPU, same tokens and same code for every checkpoint. This is **strictly better
than comparing two gates' in-run numbers**, because it removes both the eval-token-subset difference between runs
and all eval-side noise. v72 reproduced to **all six digits** on a re-run, so the harness is deterministic and the
only remaining noise is the training run itself.

It also rescued a result: `C_MTPB`'s in-run eval **crashed** in `prepare.causality_check` (a NkiDispatch lowering
failure at the 4-row eval shape) with the checkpoint already on disk. The checkpoint is written *before* the
in-run self-checks and is fully EMA-blended, so **a crash there costs nothing** — download and score it.

`experimental/offline_logit_eval.py` is the same idea for pure output-space questions, and answered two of them in
ten minutes against 2x30 min of box time.

## 3. Two of the recon's top recommendations are ALREADY SHIPPED

A fresh pass over modded-nanogpt (the useful source is the **Track-3 optimizer benchmark**, 46 entries scored as
steps-to-a-target-loss with n=8-20 seeds, not the wall-clock records table) returned seven candidates. Reading
`_muon_step` rather than trusting my own description of it:

- **NorMuon** (arXiv 2510.05491, published 3375 -> 3300 steps ≈ −0.0007) **is already there**:
  `v_mean = g.square().mean(dim=red_dim)` is the per-row second moment *of the orthogonalised update*,
  `second.lerp_(v_mean, 1 - beta2)` is its EMA at `beta2 = 0.90`, and the `(v_norm / v_norm_new)` factor is exactly
  the Frobenius renormalisation NorMuon prescribes.
- **Cautious Weight Decay** (arXiv 2510.12402, ≈ −0.0002) **is already there**: `mask = (g * w) >= 0` then
  `w.sub_(lr * g + lr * wd * w * mask)`.

**Lesson: describe the optimizer by reading it, not from memory.** Building either would have produced a null
result easily misread as the mechanism failing here.

Still missing and worth trying: **EMA-Nesterov lookahead** (PR #308, n=20 isolated on plain Muon, ≈ −0.0018) —
built this session and gating. Its collapsed recursion,
`m <- (gamma + (1-gamma)*beta_prev) m + (1-gamma) * applied_update`, was verified against an explicit
reference implementation to **7e-08**, and `beta = 0` reduces **exactly** to the base optimizer.

## 4. A vein worth mining: constants inherited and never swept

Five architecture constants have **never been swept as values** in 628 ledger rows. All were inherited from the
pre-512-width "3090 ladder" champion (10 layers x 256 wide, ~3300 steps) and carried through 70+ versions while the
model roughly doubled and the run lengthened 33%:

- `ROPE_FRAC = 0.5` — three rows exist, all at 0.5. Introduced *bundled* with `KEY_OFFSET` (the pair was −0.0032).
- `ROPE_BASE = 200_000`, `LOGIT_SOFTCAP = 11.0`, `SINK_INIT = log 4` — zero rows for any of them as values.
- **`KEY_OFFSET`'s fraction** (`hq = HD // 4`) — every row covers on/off, glue-vs-kernel, or a schedule; none the
  dose. It is a kernel **parameter**, not a constant in the kernel body, so it costs only a recompile.

The first four change only host-side tables or a learned scalar's init, so they need **no recompile at all**.
Also queued: a **joint** LR scale, because every LR was swept one at a time and a coordinated move explores an axis
no single-knob sweep touches.

## 5. Corrections to earlier findings

- `step-split-2026-09-26.md`'s "host work is 18.3 ms in a 466 ms step = a **4% CPU duty cycle**" is **wrong**, and
  with it the arithmetic that killed the hyperthread hypothesis. Measured live: **all 8 ranks at 96-101% CPU**
  (~89% user time, main thread parked in `futex_do_wait`), `thread_siblings_list` = `0,6 1,7 2,8 3,9 4,10 5,11`,
  and `Cpus_allowed_list = 0-11` for every rank (no pinning). The host is **saturated**, not 4% busy. The
  straggler axis still stays closed, but for the `PACK=4` reason and because 8 ranks on 6 physical cores is
  *forced* (and `LNC=2`/`NPROC=4`, which would fix it, is separately dead at 0.654 vs 0.485 s/step).
- Early steps of a run are **host-bound**: dt starts ~0.65 s and settles to ~0.40 s a few hundred steps in, most
  likely cold page cache on the parquet shards. **Never read a step time before ~step 500.**

## 6. Operational traps hit this session

- **`pgrep -cf <pattern>` inside an ssh command matches the ssh command's own command line.** A wait loop on
  `pgrep -cf neuronx-cc` could therefore never succeed. Use a self-escaping pattern: `neuronx-[c]c`.
- **Never `sed -i` a queue file the runner has open.** It swaps the inode; the runner keeps reading the old one, so
  the edit is invisible *and* every later `>>` append is silently orphaned. Append only, or restart the runner on a
  new file.
- **Never launch while an orphaned `neuronx-cc` is alive.** Killing a run mid-compile and launching 90 s later
  produced a run that died with `argument 'h_in' not supplied` — a half-written cache entry.
