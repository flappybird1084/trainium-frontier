## What shipped, and why it is the pattern to repeat

Both wins were **our own code failing to match the metric**, not external techniques:

1. **v57 (−0.00035, confirmed twice).** The tail EMA excluded **every** `nn.Embedding` table — ~69% of
   parameters, including the four 8192×512 token/value tables that train at `EMBED_LR_SCALE = 4.5`. The
   parameters with the largest per-step updates were the only ones never averaged. Nobody had tested the
   alternative because flipping the old switch would also sweep in the 134M bigram table. v57 adds a second EMA
   group under a numel ceiling (`EMA_TABLE_MAX`) at blend 0.65.
2. **v58 (−0.00017).** `evaluate_bpb` **never scores BOS targets** (`prepare.py` zeroes `token_bytes` for
   specials, then masks on `nbytes > 0`), yet training scored them at full weight — 0.135% of every gradient on
   a prediction the metric deletes. One line, because the fused head already implements `ignore_index=-1` in
   both directions and normalises by the valid count.
3. **v56 (risk, not score).** `record_step_boundary`'s contract charges **everything after the 5th boundary**.
   Our stop rule reserved 5 s for the checkpoint and **nothing** for the in-run causality check + eval that
   follow it: 1795.3 + 5.4 = **1800.7 s against 1800**, on a *warm* box, and 22-147 s cold. Those self-checks
   are now off by default (the scorer repeats them anyway) and `WALL_RESERVE` is 300 → 90.

**Three reusable mechanisms came out of it:**

1. **Average DENSELY-updated parameters; never sparse lookup tables.** The four small tables refresh ~3308 of
   8192 rows per micro-step (~40%), so a typical row's average is meaningful. The bigram table touches ~16k of
   262,144 rows (~6%), so a typical row was last updated long ago and averaging drags a fresh update back toward
   a stale value. This explains the win and the loss inside one family, and it prices any future
   lookup-capacity-plus-averaging proposal for free.
2. **Decontraction's premise is INVERTED here.** It assumes averaging shrinks the norm. Measured
   ||raw||/||blend||: 0.9822 (wte), 0.9859 (vte), 0.9854 (vte_mid), 0.9842 (vte2), 0.9986 (lm_head) - all below
   1, i.e. **the blend's norm is LARGER**, because our warmdown and weight decay shrink weights late so the tail
   average sits at a bigger norm than the final point. Forcing it back down undoes something useful.
3. **Fixing one thing moves another's optimum.** The ledger had already swept `EMA_BLEND` (0.1/0.35/0.5, "0.35
   best, 0.5 a wash"). That was measured with gates whose noise is twice the effect size, never tried 0.65, and
   predates v57 - once the tables are averaged too, the two groups' averages are mutually consistent and the
   matrix group can be leaned on harder. **Re-check any constant whose sweep predates a change to the same
   subsystem.**

## Method lessons that cost real time this session

- **Same-session paired reproducibility is ~0.00005**, far tighter than the 0.00025 cross-session gate figure
  (two identical 300 s screens: 673 steps / 1.101130 and 673 / 1.101177). Pair every arm; never compare across
  sessions. The box ran **2.8% slower** between two sessions hours apart, which would have flipped v57's sign.
- **A vehicle run with default knobs is a different model.** My first profile attempt silently ran a different
  hyperparameter set — 52,584 tok/s against the real 306,432. Recover the full env from a known-good run's
  `runs/<ID>.env`; never retype it.
- **Local fixed-step GPU runs need a TIME budget.** `lr_multiplier` and anything else keyed to `elapsed_frac`
  see ~0 when `MAX_TRAIN_SECONDS=36000`, so there is no warmdown and any fraction-of-run feature never engages
  — a silent no-op experiment. Set `MAX_TRAIN_SECONDS` to the run's real duration.
- **Exclusive engine time is a good FINDER and a bad BOUND.** ~100 ms of the 303 ms of graph time is
  dependency-chain slack invisible to both the exclusive total (65 ms) and the idle total (13 ms). And the idle
  figure itself is suspect: `critpath.py` sweeps only Vector/Tensor/Scalar/GpSimd/Sync, so **DMA (49% busy in
  the forward) is not in the sweep** and "no engine busy" can mean "DMA only".
- **Instruction count is something you can waste, not something you can spend.** Deleting 38% of all vector
  instructions moved the step by zero; *doubling* it (`_FMAX=256`) cost 14%.
- **Testing components of a tuned package piecemeal gives false negatives — but check the central piece before
  believing the excuse.** I suspected exactly that for ANVIL, built the missing rail as ~10 torch lines rather
  than a 4-5 h kernel port, and it lost too. The cheap falsifier saved the port.
- **The job launcher's gate pattern-matches submission filenames**, so a queue entry whose command contains one
  self-blocks and then `exit 1` kills the whole queue, silently dropping every later entry. Watch for it.

## Two latent silent-wrongness bugs to fix before ANY shape change

Both are harmless at width 512 and would corrupt results without an error at any other width:
1. `head_bwd` uses `kt = D//128` in four loops where it means `_HVC//128 = 4` (`:803-804, 858-865, 868`).
2. `post_attn_fwd_h` documents the invariant "kt == n_head and HD == _NKI_P" and writes
   `outT_out[row*n_head + i]`; if `n_head != D/128` it writes the wrong head's transposed attention output and
   the vendor attention backward gets garbage. **Add an assert `n_head == n_embd // 128`.**
