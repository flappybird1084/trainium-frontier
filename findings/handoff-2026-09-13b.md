## What Sep 12-13 established (all measured; details + numbers in flow-inference-compute.md)
1. **Multi-hop attention** (+ prehead denoise) is a real fixed-step win (-0.0083 at depth 12 locally) but LOSES under the
   fixed-time budget: full gate **0.992602 vs v40 0.985161**. Ported to Trn2 as a fused custom op (`tf_nki::hop_fwd/bwd`,
   0.62 s/step at DB16, forward verified == eager to ~1%). Eval collapse was the tail-EMA blend (use <= 0.1 with hops).
   Only lever left there: a ~2x cheaper hop (K/V reuse) - plan lever D.
2. **Compiler-flag sweep: nothing.** 9 configs (-O2/-O3 both routes, model-type, MPA, saturate-inf, fast-ctx-switch,
   implicit-downcast) all at 0.52-0.53 s/step. The step is latency-bound; the compiler is exhausted for this graph.
   **Hazard:** -O3 (any route) and ANY `NEURON_CC_FLAGS` setting corrupt the eval graph (~1.12 vs 1.053) while training is
   intact and causality passes; -O2 is clean. Never rely on those in a submission.
3. **Own flash attention: parity, not a win.** v4 (strided-load fwd) NaNs in-model even under v40's head-major layout and
   with SIDECAR_SYNC=1 -> strided INPUT DMAs are intrinsically unsafe in-graph (memory rule #11). Per-tile fwd + our bwd is
   clean but +4% step (1.0560 vs 1.0527 at 600 s); the per-step glue hoist recovers ~1 point (0.53 s) but corrupts eval
   (1.125, third trigger of the same unexplained signature). **Keep the vendor attention.**
4. **tinygrad:** no Neuron backend; would be a compiler for a non-SIMT target; removed. Fusion search needs a code
   generator that does not exist. Kernel-schedule grid: one live knob (`_HVC`), not free (2nd hard-coded 512).
5. Width 640 lost 4x historically and the kernels cap D at 512; the profile's idle engine time is per-op latency that
   scales with tile count, not reclaimable by width.

## Rules learned Sep 12-13 (also in memory / findings)
- Judge only by eval bpb; training loss lies under train/eval asymmetry (hops, EMA). A compiler flag or a new graph-produced
  kernel input can corrupt eval silently - the harness cannot catch it.
- Never run `prepare.py eval-public` standalone on the box (hangs). `trn2_job.sh` self-matches the vehicle path (always
  blocked); `trn2_run.sh` refuses on a busy device; launch queue runners from a shell whose cmdline has no `python`/`torchrun`.
- Never ship the vehicle while a queue has unlaunched lines (they pick up the new source). Import-guard before overwriting.
- Local `gpu_gdn.sh`: `R1_VMEM_KB=48000000` for depth-12 multi-hop eval; multi-hop trains at DB=2.
- Strided-pattern DMAs (input or output) on graph-produced tensors are unsafe inside the compiled graph (rules #9, #11).
