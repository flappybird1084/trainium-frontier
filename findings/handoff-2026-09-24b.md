## READ FIRST: the step is LATENCY-BOUND (established late on 2026-09-24)

Everything below this section was written BEFORE the first instruction-level NEFF profile this project has had.
The governing fact, and the one that should shape all future work:

**No engine is saturated** (vector 69%, tensor 49%, scalar 48%, dma 40%), and deleting **38% of ALL VectorE
instructions** with verified bit-identical math moved the step by **nothing** (646 steps vs 646, 0.482 vs
0.482 s). So **element counts, byte counts, call counts and instruction counts are all the wrong currency** -
the wall is the dependency chain through the graph. See `findings/instruction-profile-2026-09-24.md`, whose
own title had to be retracted.

**Method lesson worth more than any lever here: per-instruction DURATION in a profile is not critical-path
time.** An instruction can take 374 ns and cost the wall zero.

This retro-explains every null of 2026-09-24 (bf16 gradients, merged/reordered collectives, the collapsed
scalar AdamW, the bf16 bigram table, the wide rotary): all throughput optimisations on a latency-bound machine.

**The only direction that fits the diagnosis is FEWER, LARGER KERNELS.** The file has already had that program
(`LAYER=op`, `PRE_BWD=fused`). What is left is the **vendor attention backward: 101.5 ms = 21% of the step**,
which has no external lever (no tile-size parameters; `sliding_window` does nothing at seqlen 1024; our own
version measured slower twice). Replacing it is a multi-day project with two prior failures - go in with that
expectation or not at all.

## What is now CLOSED, with numbers (do not re-litigate any of this)

The non-fwd/bwd phase is `grad_sync` 59 ms + `optimizer` 47 ms (of which `gather` 28 ms). **Five** mechanisms
were proposed for the 59 ms; **four were refuted by direct measurement** and the fifth is not actionable:

1. **Byte count: DEAD.** Halving the gradient bytes of **all** 218.1 M sharded elements moves `grad_sync` by
   **0.000** (0.059 fp32 / 0.059 at 77% bf16 / 0.058 at 100% bf16; 646/648/643 steps). Re-confirms
   `S_V26_OPHEAD_GB16` from v26, which I should have grepped for before building.
2. **Call count: DEAD.** `rs_probe.py` measures `reduce_scatter` at ~60 GB/s, byte-bound, with only ~0.2 ms of
   fixed cost per call. All nine production collectives back-to-back = **~17 ms**; 32 of the 16.8 MB ones =
   11.41 ms total (0.36 ms each). Splitting the big one into K=1..32 chunks does nothing (8.4-11.4 ms).
3. **Ordering / the gaps between the calls: DEAD.** `RS_BATCH` builds every (output, input) pair first - both
   100 MB `torch.cat`s included - then issues all nine consecutively. `grad_sync` 0.059, **unchanged**; 650
   steps, inside the 643-650 noise band.
4. **What it actually is: cross-rank waiting.** The whole phase now reconciles. The `PROFILE` timer takes
   `t_fb` *before* the `PROFILE_SKEW` block and computes `grad_sync = t_gs - t_fb`, so **`grad_sync` CONTAINS
   the skew**: 61 ms = **43 ms of barrier wait + ~18 ms of real collective**, and that ~18 ms is exactly
   `rs_probe.py`'s ~17 ms for the nine reduce_scatters back-to-back. (The subagent audit claimed `PROFILE_SKEW`
   *removes* the wait from `grad_sync`; it does not - `grad_sync` reads 0.059-0.061 with and without it.)
5. **Thread contention is NOT the cause** - `OMP_NUM_THREADS=1 MKL_NUM_THREADS=1` changed nothing
   (total 0.483 vs 0.485, skew 0.043 both).

### The straggler lead: RESOLVED THE SAME EVENING, AND DEAD

`SHARD_ROTATE=3` (rotate the shard list by a constant: every rank gets different data, same rank order, same
hardware) gave `r0 0.372 r1 0.371 r2 0.371 r3 0.377 r4 0.377 r5 0.372 r6 0.372 r7 0.391`.

**Rank 1's 19 ms followed the DATA** (0.390 -> 0.371; r3/r4 picked up a milder ~5 ms instead). **Rank 7's did
not move** - 0.389-0.391 in all three runs. So **rank 7 is structurally ~19 ms (5%) slower whatever it is fed**,
and since the step is set by the slowest rank, the rotated run's maximum is *still* 0.391. **Perfect data
balancing buys exactly zero while one core is structurally slow**, and that cannot be fixed from `train.py`:
giving rank 7 a smaller micro-batch means per-rank tensor shapes (a different NEFF per rank) and per-rank
gradient weights.

**So the whole non-forward/backward phase is closed, with the mechanism fully accounted for:** `grad_sync` =
~43 ms waiting on a structurally slow core + ~18 ms of real collective. Do not re-open it. The detail below is
kept because it is how the result was reached.

### How it was found (worth ~3.9% if r7 had been fixable)

Per-rank fwd+bwd, **reproduced identically across two independent runs**:

```
reference       r0 0.372  r1 0.390  r2 0.371  r3 0.371  r4 0.371  r5 0.372  r6 0.373  r7 0.391
thread-limited  r0 0.371  r1 0.390  r2 0.373  r3 0.372  r4 0.373  r5 0.374  r6 0.374  r7 0.389
```

Six ranks at 0.371-0.374 and **exactly two - ranks 1 and 7 - at 0.389-0.391**, consistently, averaged over 30
steps with different data each step. The step is set by the slowest rank. Of the 43 ms wait, **~19 ms is this
systematic offset (3.9% of the step)** and ~24 ms is per-step jitter in which rank happens to be slowest; the
jitter is probably not recoverable, the 19 ms might be.

It is **not** data-dependent host cost (that would move between ranks), **not** the sharding (fwd+bwd device
work is identical per rank, and the padded MLP plan would penalise r6/r7, not r1/r7), and **not** thread
contention. Two candidates remain, with opposite conclusions:

- **the data split** - the rank -> shard/offset mapping gives ranks 1 and 7 systematically more work (shorter
  documents -> more boundaries -> more host planning and more doc-mask work), in which case rebalancing pays;
- **hardware/topology** - NeuronCores 1 and 7 are structurally ~5% slower, in which case nothing in `train.py`
  fixes it.

The discriminator that settled it is `SHARD_ROTATE` in `train3_s16.py` (diagnostic only, never ship it:
it changes which shards the run sees). `prepare.py` derives the rank internally so the rank -> data mapping
cannot be shifted from `train.py`, but it accepts a `shard_ids` **list**, and rotating that list by a constant
gives every rank different data with the same disjoint partitioning and the same rank ordering.

Also closed: the **sparse / `all_to_all` bigram gradient exchange** (each rank touches at most 16384 of 262144
rows, so 93.75% of that collective is provably zeros - correct, and worth nothing, because the phase does not
respond to byte count); the **scatter's power-of-two slot ladder** (~79% padding on the bigram plan, but the
file's own measured figure is ~9 us for a *padding* tile, so a finer ladder is worth ~1.5 ms = 0.3%, not the
~4.5 ms an average-tile-cost estimate suggests); **embedding/head tying** (declined, not measured: the head is
initialised at std 0.001 with its own LR and betas while the token table has a 4.5x LR scale, so tying is
several gates of re-tuning plus summing gradients from two paths, not one screen).

## The two real changes, and the traps found while building them

**`BTE_BF16`** - hold the bigram table *and its sidecar gradient buffer* in bf16. It is the one form of byte
reduction that still pays, because it needs **no cast**: the probe measures bte's reduce_scatter at 8.89 ms fp32
vs 4.62 ms bf16. `GRAD_BF16` measured as a wash precisely because its full-size cast pass costs ~8.4 ms and its
saving is ~8.5 ms. Safe for bte only: 16384 hashes over 262144 rows means almost every row takes one
contribution, whereas the 8192-row token tables accumulate hundreds of adds per row and would lose them in bf16.
Traps cleared: the fp32 master must be forced (`p.data[lo:hi].clone().float()`); the fused Muon/AdamW kernels
require an fp32 `(pshard, gshard)` pair behind a `try/except` that would **silently** fall back, so the bf16
shard is cast up after the collective; both embedding kernels staged rows in a hardcoded `nl.float32` SBUF
buffer, now `dtype=table.dtype` (a converting *indirect* DMA could have reinterpreted bytes rather than failing);
and the checkpoint writes bf16 replicas back as fp32 so the scorer sees a dtype-identical file.
**The EMA trap**: `ema_params` is cloned from `p`, so a bf16 replica would make `e.lerp_(p, 0.003)` a silent
no-op. Safe here only because the submission already excludes every `nn.Embedding` weight from the EMA
(`train.py:3682`) - **verify that before extending bf16 replicas to any non-embedding param.**

**`FLAT_OPT2`** - the small-parameter AdamW spent **8.4 ms/step updating 93 numbers** in ~23 eager launches.
The params become views of the persistent flat tensor (the 8 write-back copies vanish) and the update expression
collapses. Verified bit-identical to the original in float64 at steps 1/7/400.

## Method failures worth keeping

- **I over-claimed twice more today** (that is five times on this project). First "the collectives run at
  ~13 GB/s so bytes are the whole cost" - which was just 59 ms divided by 763 MB, a quotient with no mechanism
  behind it, contradicted by a `CCPROBE` number already in the ledger. Then "the cost is fixed per call, ~30 ms
  for the five small tables" - from a per-section split whose **parts summed to 172.6 ms inside a 62 ms phase**.
- **New rule: before believing any per-section breakdown, check that the sections sum to the phase.** The cause
  was averaging calls 1-40 when the *first* call of each collective pays a one-time setup; one ~1.2 s init over
  40 calls reads as exactly ~30 ms/call. Fixed in `train3_s15.py` (accumulate only calls 10-39).
- **`skew=0.000` in every `PROFILE` line is an unpopulated field, not a measurement.** It is only accumulated
  under `PROFILE_SKEW=1`. I read it as "rank skew is zero" for hours; it was 42 ms.
- **Grep the ledger for a knob before building anything on it.** `GRAD_BF16` and `LOADER_DEV=cpu` had both been
  screened and rejected in earlier sessions; I re-derived both from scratch.
