# Document-mask tile skipping in attention: waste, feasibility, verdict (2026-09-28)

**Verdict: do not build it.** It is real waste, but at the vendor kernel's tile size it is small. The ledger already has a device run that skipped *more* tiles than this would, and it bought no measurable steps. Best realistic gain is about −0.0001 to −0.0002 bpb, for 12–20 h of high-risk kernel surgery.

## 1. Waste, measured on real data

Method: I used prepare.py's `make_dataloader` read-only, exactly as the vehicle calls it: PACK=4, 4 rows of 4097 tokens, reshaped to 16×1024. I built bounds the same way as `doc_bounds`, with the causal clamp. The run covered 400 batches (6,400 rows). The cumulative fraction was still rising slightly at the end (100 batches 20.7% → 400 batches 22.3%), because the loader's early document buffer is atypical, so the steady state is about +0.5 pt above the numbers below. There are 1.55 BOS tokens per row, and 7.5% of rows contain no document start at all.

Tile sizes come from the nkilib source:
- **Forward** (`attention_cte`): QK matmul, mask and exp run on tiles of 128 q × **512** k (`_K_TILE_SZ`). The PV matmul runs on 128 q × 128 k.
- **Backward** (`attention_bwd`): q tile 128, k tile `psum_fmax` = **512**. `tile_required` is decided at 128 q × 512 k.
- With seq=1024 there are only two 512-wide k-tiles. The only tiles that can ever be skipped are (q-group 4–7, k-tile 0).

| granularity | causal tiles/row | entirely doc-masked |
|---|---|---|
| 128 q × 512 k (fwd QK/exp, all of bwd) | 12 | **8.4%** |
| 128 q × 128 k (fwd PV) | 36 | **22.3%** |
| element-level (ideal) | — | 36.7% |

Per q-group, k-tile 0 is fully masked 0 / 0 / 0 / 0 / 0.2 / 16 / 34 / 51% of the time.

The fractions are **identical for 4×128 and 2×256**, because tiling runs along the sequence; head dim only changes d-tiles. The ms differ because the kernel cost differs.

**Converted, assuming time scales with tiles computed (undiscounted):**

| | 4×128 (60 ms attn/step) | 2×256 (38 ms) |
|---|---|---|
| runtime skip at kernel grain (~8.4% bwd, fwd mix ~15%) | ~6 ms = 1.4% step → −0.0005 | ~4 ms = 0.9% → −0.0003 |
| new kernel at 128 grain (22%) | ~13 ms = 3.2% → −0.0011 | ~8.5 ms = 2.0% → −0.0007 |
| element-ideal (37%) | ~22 ms → −0.0018 | ~14 ms → −0.0012 |

**Discount, calibrated on our own ledger:**
- `Q_SWA256` used the vendor's native, compile-time sliding-window skip on both kernels. It skipped **16.7%** of the backward tiles and **42%** of the forward PV tiles. That is more than the doc-skip achieves even at 128 grain.
- The measured result was fwd_bwd −8 ms, 649 vs 646 steps (+0.5%, inside noise).
- `Q_SWA512` gained nothing.
- The exclusive-time study found the attention backward is only ~3.5 ms exclusive: the engines overlap it with other work.

Skipping attention tiles therefore frees mostly overlapped time. Realistic ranges:
- Kernel-grain doc-skip: **≤0.25% steps (≈ −0.0001)**.
- A 128-grain rewrite: **≈0.5% steps (≈ −0.0002)**.

A runtime version would also pay dynamic-control-flow overhead, which a static skip does not. So these are upper bounds.

## 2. Feasibility on this toolchain

**Runtime skipping is expressible, but nothing ready-made does it:**
- Device nki 0.5.0 (checked in the local `.venv-nki`) has `nl.dynamic_range` (runtime start/stop; the step must be static) and `nisa.register_alloc/register_load/register_store`. It does **not** have `fori_loop`/`while_loop`; those are 0.6-only.
- In 0.6, `dynamic_range` is deprecated in favour of `fori_loop`/`while_loop`.
- There is no runtime `if`. The idiom would be `dynamic_range(0, flag_reg)` with a trip count of 0 or 1, or `dynamic_range(k_lo_reg, 2)` over k-tiles.
- The per-(row, q-group) first-k-tile index could be computed in torch from the bounds and passed as an int32 tensor, then `register_load`ed. That respects the rule that a kernel argument cannot drive a trace-time decision: it is a runtime register, not a Python value.
- Predication exists (`tensor_copy_predicated`, `select_reduce`, `range_select`), but it masks values. It does not skip matmuls.

**The vendor kernels have no runtime or block-sparse mode:**
- `attention_cte`'s `dynamic_sel_mask` (used for CP, SWA+CP, prefix caching and `kv_used_len`) is **range_select masking over the full tile set**. `kv_used_len` also asserts non-causal and non-packed.
- `attention_bwd`'s `tile_required` is a pure-Python list decided at trace time.
- `attention_segmented_cte` / `sequence_bounds` do use `dynamic_range`, but only for paged-KV **inference**: there is no backward.

**What building it means:**
- Rewrite the forward's statically unrolled k-loop, which relies on Python-int PSUM bank indices, 2048-wide large-tile pipelining and per-tile buffers. Rewrite the backward's per-group k-loop.
- Both would use register-offset DMAs and matmuls inside a dynamic loop, and they must work in-graph under the tracer rules: 128-row-aligned DMAs, no strided output DMAs.
- Dynamic loop boundaries also fence the compiler's cross-engine scheduling. That is exactly the overlap that makes attention cheap today.

**Static alternatives:**
- **Align document boundaries to tiles.** A compile-time `tile_required` is valid only if the tile is masked in *every* row. That needs a forced boundary at a fixed position (512) in every row, which is just segmentation. Aligning document starts to 128/512 without a fixed position gives no static pattern. Padding to alignment wastes compute on pad tokens and still leaves the pattern row-dependent.
- **Fixed 2×512 segments.**
  - Gain: the static skip would drop 4/12 kernel tiles and 16/36 PV tiles (~33–44%, ~20 ms undiscounted at 4×128). Using the SWA calibration, that is roughly +0.8–1% steps, ≈ −0.0003.
  - Cost: **22.1% of training tokens currently attend to ≥512 tokens of context** and would lose it. Our own context data point is 2048 → +0.0039, and the 27-Sep session closed this axis ("shrinking context buys ~nothing and pays full quality cost").
  - A plausible +0.003–0.01 loss swamps −0.0003.
  - It also creates a train/eval attention mismatch unless eval segments too, which hurts eval. The reviewer rejects this pattern.
- A hybrid (some rows segmented, routed to a second static kernel variant) has the same price, scaled down.

## 3. Recommendation

**Not worth building in the ~34 h left.**
- **Gain:** realistically −0.0001 to −0.0002 bpb, below gate noise, so it could not even be confirmed.
- **Cost:** 12–20 h touching ~5,900 vendor lines, the scantily supported nki-0.5 `dynamic_range`, and in-graph device debugging.
- **Risk:** a silent kernel fallback here costs 7× step time (the C_PRE3 lesson).

**If anyone wants a number before closing it,** the cheapest device check needs no new kernel. Run the current vehicle with the vendor `sliding_window=384` on both attention calls for a ~150-step step-time-only A/B (ignore bpb).
- Window 384 statically skips exactly 1/12 backward tiles (8.3%, which matches the doc-skip 8.4%) and 28% of forward PV tiles (vs 22%).
- It is therefore an overhead-free **upper bound** on kernel-grain doc-skipping.
- If its step time moves <1%, the idea is dead at any granularity the vendor structure allows. `Q_SWA256` already says it will.
