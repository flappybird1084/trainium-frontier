# BTE_BF16: the three gates that "rejected" it measured nothing (2026-09-27)

`submission_v53_clean_bte_bf16.py` was gated three times at full 1800 s and rejected as a wash
(0.971630 / 0.971847 / 0.971556, mean 0.971678 against v52's mean 0.971674 — a difference of 0.000004).
`handoff-2026-09-24b.md` records the verdict as "v53 REJECTED — a wash. v52 stands… do not promote them",
and `findings/comm-bytes-2026-09-24.md` closes the gradient-byte direction on the same evidence.

**That verdict is void. In the file that was gated, the change was dead code.** Ledger row 660
(`R_BTE_RETRACT`) carries the retraction; this file is the mechanism.

## Defect 1 — the cast never executed

`make_v53.py` inserts the cast immediately after the `synthetic_y` line. In v52 there is exactly one such
line, and it is the second line of the `if args.compile_only:` block — a block that ends in `return` before
any training happens. The launcher never passes `--compile-only`, so the bigram table stayed fp32 for the
entire run of all three gates.

The patch script's own docstring explains the placement as "before the compile-warmup block (which does its
own synthetic forward/backward and its own setup_sharding) so both traces see bf16 and the run pays ONE
compile, not two". There is no compile-warmup block in the live path — the author was describing the
`compile_only` block itself, which is a separate early-return mode, and placed the cast *inside* the thing it
meant to precede.

## Defect 2 — the wrong master shard was forced to fp32

`setup_sharding` has two `pshard` clone sites: one for the padded 3-D Muon stacks (`p.data[lo:hi]`) and one
for everything that divides evenly (`p.data[rank * per:(rank + 1) * per]`). The patch forced `.float()` on
the **padded** one. The bigram table is 262144 rows over 8 workers, so it divides evenly and takes the
*other* branch.

Had the cast run, the bigram master shard and its gradient shard would both have been bf16. The fused NKI
AdamW requires an fp32 `(pshard, gshard)` pair, and it is called behind a `try/except` that sets
`self.use_nki = False` — so the failure would have silently disabled the **entire** NKI optimizer, Muon
included, and read as a large throughput regression with no error in the log.

## Why the three gates read 0.000004

Every other hunk in the patch is a no-op while the table is fp32: the two kernels' `dtype=table.dtype` resolves
to `nl.float32`; `.clone().float()` returns the same tensor; the `reduce_gradients` dtype branch never fires;
the `gather_params` bf16 branch never fires; the checkpoint's bf16 test never matches. So v53 was
**behaviourally identical to v52**, and 0.000004 is exactly the right answer to the question the gates asked.

`make_v54.py` branching from v52 rather than v53 was therefore **correct on the evidence available**. Nothing
was dropped by accident, and there is no lost-work story here — only a null result that was never a
measurement of the change.

## What the live measurement actually says

The vehicle implementation (`train3_s14.py` / `train3_s15.py`, flag `NEURON_COMPETITION_R1_BTE_BF16`) is
correct, and the flag was confirmed live at startup by its own print in the 300 s `Q_ALL` screen. That screen
measured, paired against `Q_REF`: grad_sync 0.057 vs 0.059, optimizer 0.046 vs 0.049, gather 0.0264 vs 0.0286,
total **0.480 vs 0.485 (−1.0%)**, and 653 vs 646 steps. Two mechanisms, both real:

- the gradient reduce_scatter of the table halves its bytes **with no cast pass** (standalone probe: 8.89 →
  4.62 ms). This is precisely why the full-size `GRAD_BF16` was a wash — its cast cost ~8.4 ms against an
  ~8.5 ms saving.
- the parameter all_gather writes `p.data` directly, deleting a ~805 MB/step converting copy and a 256 MiB
  staging buffer.

Note the tension with row 527 of the ledger ("the gradient reduce_scatter is NOT byte-bound: 0.059/0.059/0.058
for REF/GBF16/GBFPAD"). Both can be true — `GRAD_BF16` halved bytes *and* paid a cast, so a null there does
not price a byte reduction that costs nothing. The honest position is that only the gather half has
independent support (`GATHER_BF16` +0.6%), and the reduce half is unpriced.

## The port into `train3_canon.py`

Behind `NEURON_COMPETITION_R1_BTE_BF16` (default `"0"`), ported from the vehicle rather than from the patch
script, seven sites:

1. the cast, in a module-level `apply_bte_bf16()` called after `setup_optimizer()` and before
   `setup_sharding()` — and also in the `--compile-only` block, so a cache-warming run traces what the real
   run traces;
2. `setup_sharding`: `.float()` on **both** `pshard` clones;
3. `reduce_gradients`: when the gradient dtype differs from the shard dtype, reduce at the gradient's dtype
   into a lazily allocated bf16 `gsmall` and cast only the 1/8-size result up;
4. `gather_params`: the bf16 replica is the collective's destination directly;
5. `embed_gather_v2`: staging buffer `dtype=table.dtype`;
6. `embed_scatter_add_v2`: same (here `table` is the gradient accumulator and `dma_compute` adds into it in
   place, so all three operands must share a dtype). The `_x4` variant is untouched — it only ever sees the
   four fp32 token tables;
7. `save_checkpoint`: bf16 tensors written back as fp32, so the scorer sees a dtype-identical file.

Plus one fix that neither v53 nor the vehicle has: the sidecar's `index_add_` fallback did `g2.float()`, and
`index_add_` rejects a source whose scalar type differs from the destination. Against a bf16 accumulator that
raises, uncaught, which would turn a recoverable kernel-lowering failure into a disabled sidecar. It now
follows the accumulator's dtype.

The two tail-EMA exclusions are now **enforced** rather than assumed: `apply_bte_bf16` raises unless `bte` is
an `nn.Embedding` (what excludes it from EMA group 1) and `numel > EMA_TABLE_MAX` (what excludes it from
group 2). A bf16 EMA buffer would make `e.lerp_(p, 0.003)` a silent no-op, and that would read as a mediocre
score rather than an error — the exact failure class this project keeps paying for.

Verified locally on CPU, no device job: with the flag off the file reproduces the pre-edit file's losses
**bit-for-bit in hex float** over two full steps (init → sidecar gather → forward → backward → packed scatter
→ all nine ZeRO collectives → AdamW + Muon → `gather_params` → checkpoint); `num_params` is 205,520,989 either
way; `prepare.py check` passes.

## The forced coupling, and its measured cost

You cannot hold the table in bf16 and its gradient accumulator in fp32. `torch` rejects
`p.grad = <fp32 tensor>` on a bf16 parameter, so the sidecar's accumulator dtype follows the table's, and an
fp32 accumulator would require exactly the full-size cast pass this change exists to avoid.

So the scatter accumulates in bf16. Measured error of bf16 sequential read-modify-write accumulation over 512
channels (200 trials of standard normals, median):

| adds into one row | relative error |
|---|---|
| 1 (already true today — the gradient *rows* are bf16 either way) | 0.16% |
| 16 | 0.5% |
| 41 | 0.8% |
| 201 | 1.7% |

16384 hashes over 262144 rows means almost every row takes a single contribution; the hottest bigrams take
41–201. So the change costs roughly **1.5% of relative gradient accuracy on a few hundred hot rows** and
nothing anywhere else. That is the price a gate has to justify.

## Four things I am guessing rather than deriving

1. **`dtype=table.dtype` yields a trace-identical NKI kernel for the fp32 tables.** Derived — it resolves to
   `nl.float32` — and supported by every `train3_s15` device run carrying that line with the flag off. I
   cannot lower a kernel locally to prove it.
2. **The bf16 scatter-add has never provably been lowered at 16384 slots per launch.** The bf16 *gather* is
   device-validated by the `Q_ALL` screen. The bf16 *scatter* was validated only under the old
   `scatter_rounds` planner (power-of-two slot counts); the v70/v71 packed planner always issues
   `SCATTER_BINS * 128 = 16384`. Same lowering, different dtype — low risk, and the failure mode is loud
   (`print0` plus the now-working `index_add_` fallback), not silent.
3. **The gain on today's step.** The only live measurement is −5 ms on a 485 ms step from 2026-09-24. Scaled
   naively to a 410 ms step the same two mechanisms are ~2 ms, i.e. ~+0.5% steps ≈ −0.0001 bpb, below
   single-gate noise (~0.00025). This must be read from **step count**, not bpb. See the DMA-descriptor
   analysis of 2026-09-27 for why the naive scaling may badly understate it.
4. **At `world_size == 1`** the flag makes the bigram AdamW state bf16, because `setup_sharding` returns early
   and the step runs on the replica. Irrelevant to the 8-way launch; do not use the flag for single-core dev
   numerics.

## The transferable lesson

This is the third time on this project that a knob was priced from a run in which it was not active (see the
EMA cold-start retraction, and `C_PRE3`'s silent kernel fallbacks in `session-2026-09-27.md`). The vehicle got
this right by printing a one-line confirmation at startup; the frozen submission had no such print, and
nothing checked. **A frozen submission that carries a behavioural change should print that the change is
live, and the gate log should be grepped for that line before the result is believed.** Cheap, and it would
have saved three 30-minute gates and a closed direction.
